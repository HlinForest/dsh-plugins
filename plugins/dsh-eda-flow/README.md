**文字需求与规格书正文 → Harness 当前模型 → MCP 操作与返回 → 原理图、BOM 和检查 → 工程师确认。**

新项目采用 `text-mcp` 模式。显示板默认输入是一份可查看、编辑和粘贴的完整中文任务书；生成时直接放进模型上下文，不加载旧工程对象包。模型自行组织通用 MCP 操作、读取结果并修正。第一步人工确认；第六步 PCB 明确为“本轮未执行”。保留七步和三栏窗口，原有项目仍可查看并标明历史来源。

## 0.4.0 文字执行流程

- 需求和规格书正文直接输入。附件无法读取时，可粘贴对应型号、版本、页码的相关内容继续；未读到的文件不会显示已读。
- 模型可提出待补问题、调用 MCP、检查返回、修正参数及结束当前步骤。工具错误回传模型；没有实际工程或检查结果不能仅凭模型文字标为生成完成。
- CAD 创建与修改由包内通用 MCP 服务完成；模型不执行任意 Python，不进入旧固定对象转换器。宿主沿用已有模型选择、工具注册和工具执行接口。
- BOM、PDF、网表及 ERC 从本次工程导出。原始对象和非物料检查声明分别记录；上游输入变化后，下游标记待更新。
- 新模式不提供固定调用序列的“空目录重放”。独立再生成需要新的模型执行，不能把重放当作独立模型验证。

开发验证使用模拟模型协议和真实 KiCad MCP；**Harness 的真实模型验收仍待验证**，不消耗 DSH 模型额度。源码包不会自动替换正在运行的已安装插件，也不会重启 Harness。

## 运行依赖

保留既有 Windows / Node / Harness / KiCad 环境。新增通用 MCP 服务需要 Python 3.10+ 和 `jsonschema`，依赖见 `mcp/requirements.txt`；`mcpPython` 可指定已安装这些依赖的 Python，未设置时沿用 `kicadPython`。模型密钥仍由 Harness 管理。当前开发机的验证路径不是内网安装路径；内网应填写实际工具路径。

以下 0.3.x 说明是历史兼容记录，不代表新文字模式仍需加载旧对象包或生成 PCB。

## 0.3.4 内网资料读取与操作引导

第二步新增“检查资料读取”，对照 Harness/Node 与 KiCad Python 的哈希和 TSD 保护头，诊断不含文件正文、不调用模型。CSV 等资料变化从第二步阻止执行，保留未变化的任务确认；真实任务或调整要求变化仍需重新确认。资料恢复一致后可重试，不会修改校验基准或跳过保护格式。

移除来源、器件及 BOM 表格中无作用的勾选框。每一步写明点击顺序、默认资料、补充位置和缺项处理；第二步无需勾选来源记录或重新上传 AD。[更新与诊断步骤](../../docs/update-eda-flow-0.3.4.md)。

## 0.3.3 确认状态与输入入口

新增页面／后台版本核对，确认响应不完整时读取已保存状态；默认资料和待确认项都有直接入口。[更新与生效检查](../../docs/update-eda-flow-0.3.3.md)。安装完成后需核对实际运行版本，仅关闭设计窗口可能保留旧后台。

## 0.3.2 确认与启动修复

修复确认失效后仍跳到下一步、任务启动失败反馈不明显的问题；按文件内容核验，记录具体变化文件。[已有安装更新命令](../../docs/update-eda-flow-0.3.2.md)会保留原项目、模型配置与登录，无需填写工作目录。

## 使用

0.4.0 的包、依赖和验收边界见 [文字 MCP 迁移说明](docs/text-mcp-0.4.0.md)。环境：Windows x64、Node ≥22.19、Harness 0.2.0-rc.2、KiCad 10.0.6，以及带 `jsonschema` 的 Python。沿用 Harness 的模型选择和登录。旧完整离线包仍是 0.3.x，不能替代本次 0.4.0 插件包。

1. 点击 Harness 的“电路设计”，在独立窗口操作；再次点击会返回已有窗口。点击“新建项目”，选择空白输入或显示板输入。
2. 核对第一步完整任务书；第 3 步可粘贴规格书正文，并注明型号、版本、来源和页码。
3. 第一阶段保存并人工确认。后续整理文字、生成原理图和核对 BOM。右栏 AI 助手的建议经采用才写入输入；模型待补问题需明确回答后重新执行。
4. 查看图纸、文件、检查和缺项，确认后进入下一步。修改输入会使相关结果失效。
5. 第 6 步显示本轮未执行，可进入第 7 步查看实际检查和交付文件。

工程师填写普通表单或选择本机文件，无需预制内部 JSON。页面支持全屏图纸、资料分段查看、原始线宽图下载。所有文件保存在配置的工作区中。

## 输入与工具

- `cases/display-board/default-text.txt` 是新显示板默认文字；包含公开坐标和公开修正问答，不包含 CAD、原生对象 JSON、预制调用序列或生成脚本。
- 四个通用 MCP 操作负责创建、应用明确图元、读取和真实检查导出；没有显示板业务模板。精确连接与坐标来自任务书，不能宣传为模型自行推导原版面。
- 历史工程对象包与转换器仅留作旧模式兼容，新文字流程不使用它们。
- 规格书型号不完整、正文未提供和附件不可读都是明确待补事项；不以相似型号补齐后宣称准确。

## 验证与限制

本机禁止付费模型调用。发布记录区分真实 KiCad 执行、模拟模型接口测试、真实模型待验证；模型失败不会降级成预置答案。

Codex 已用同一份最终文字完成两次隔离生成，并与确认过的 AD 原始记录独立比较。此结果证明本次文字要求和通用工具可完成指定原理图；不能替代 Harness 真实模型验收。内网没有 AD 核验基准时，不显示与原 AD 一致的结论。原电源图形采用同名标签映射，部分准确规格书和采购型号仍缺；PCB、制造和实物性能未验证。

MCP 写入限定本次任务目录，调用参数、结果和文件摘要保留。这是应用层约束，输入快照与哈希核验不等于操作系统隔离。旧模式架构另见 [历史架构与核验](docs/architecture-v2.md)。

## 0.3.0 三栏独立窗口

正式界面按已确认的三栏稿实现：左侧七步流程、中间页签与数据、右侧按项目及步骤隔离的 AI 助手。窗口优先使用独立桌面运行时，由插件后台提供仅绑定回环地址的认证接口；凭据和模型调用仍在 Harness 后台完成。插件只注入宿主图标入口，不注入聊天遮罩、工程浮层、快捷键或全局样式。

项目切换只选择已有工程，名称、创建时间与短编号共同区分。仅“新建项目”创建可见实例；重试与空目录重放保留在操作记录。支持改名、上传本机文件、查看输入、模型错误详情和实际生成文件。已有项目不合并、不删除。

本地开发验证使用 `test/serve-ui.mjs` 和模型替身，均不进入安装包；正式安装没有模拟模型开关或硬编码回复。具体检查见 `docs/ui-0.3.0.md`。
